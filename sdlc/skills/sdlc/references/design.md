# Design 阶段

Design-1 与 Design-2 共用 `001-设计文档.md`。Design-1 定稿业务与概要层级，Design-2 重新打开同一文档并补齐技术层级；不要为两个阶段生成两份主文档。

## Design-1：概要层级

1. 确认任务目录、系统名称、目标、范围外内容和验收口径。
2. 生成或更新 `onlyAI/structured-request.json` 与 `onlyAI/context-scan.json`，记录需求、约束、已验证事实和未知项。
3. 按 `task-state.md` 初始化任务；已有机器状态时校验当前阶段为 `design-1`。
4. 使用 `assets/设计文档模板.md` 创建或更新 `001-设计文档.md`。不要调用 brainstorming。
5. 完成背景目标、事实约束、业务流程、系统边界、主要风险和验收方向；技术设计章节可标记为“Design-2 补充”，不能伪造细节。
6. 扫描业务语义、外部依赖、架构选择、性能风险和验收标准。每个待确认项直接写入设计文档的 Grill 决策记录；记录过长时才使用 `assets/待确认模板.md` 创建 `001-设计文档-评审记录.md`。
7. 有待确认项时使用 `update --document-state reviewing --open-items [N]` 和 `review --status in_progress`，按 Grill-with-docs 逐项处理；每次决定立即回写设计文档及受影响章节。
8. 当前层级待确认项归零并完成一致性检查后，运行 `review --status completed --evidence [评审记录]`，将“当前完成层级”标记为“概要设计”，再使用 `update --document-state final --open-items 0` 和 `complete`，状态投影为 `design-1 / 已完成 / 25%`。没有真实待确认项时不强制创建空评审记录。

## Design-2：详细层级

1. 校验 Design-1 已完成且机器状态无未确认项、无阻塞；运行 `start --phase design-2`。
2. 继续编辑同一份 `001-设计文档.md`，把文档状态恢复为草稿，不创建详细设计文件。
3. 补齐对象与状态、接口/事件/数据库契约、并发与幂等、权限、异常与降级、可观测性、迁移兼容、预计改动范围和验证策略。
4. 新的待确认项继续写入同一 Grill 决策记录；重大架构与数据决策写入 ADR。
5. 对照概要层级复核目标、边界、契约、风险和验收标准。出现待确认项时按 Design-1 的 `review` 命令记录评审过程与证据；待确认项归零后把“当前完成层级”标记为“详细设计”。
6. 使用 `update --document-state final --open-items 0` 和 `complete`，状态投影为 `design-2 / 已完成 / 45%`。

Design 阶段不生成施工文档；`002-施工文档.md` 只在 Implement 阶段基于已定稿设计生成。

## 旧任务兼容

已有 `001-概要设计.md` 与 `002-详细设计.md` 的任务不机械覆盖历史文件。再次进入设计阶段时，把仍有效的内容和决策合并到 `001-设计文档.md`，在文档中注明来源；确认合并完整后停止继续维护旧文件。只读历史任务可以保留原结构。

## 退出条件

- 当前阶段要求的设计层级已完成并在同一主文档中可定位。
- 机器状态未确认项为 `0` 且无阻塞项。
- 所有已解决决定都已回写主文档，重大长期决策已记录 ADR。
- 不存在未说明的占位符、互相冲突的章节或无验证口径的目标。
- 分阶段模式下，用户已确认达到共同理解。

交付阶段结果前运行 `validate`。Solo 只能自动决定低风险、可逆且不改变需求口径的细节。
