# Solo 模式

Solo 只串联标准工作流：`design-1 → design-2 → implement → test → close`。它从当前可信阶段推进到测试完成，并自动执行 `sdlc-close` 收口为 `done / 已关闭 / 100%`，但不突破用户授权和高风险决策门禁。Debug 和 Script 是独立流程，不属于 Solo；当前 `workflow` 为 `debug` 或 `script` 时拒绝启动 Solo，并提示使用对应入口继续。

## 阶段检测

同时检查 `onlyAI/task-state.json`、`status.md` 投影、主文档和验证证据：

- design-1 完成：`001-设计文档.md` 的概要层级已定稿且未确认项为 `0`。
- design-2 完成：同一设计文档的详细层级已定稿且未确认项为 `0`。
- implement 可编码：`002-施工文档.md` 已经 Grill-with-docs 压测、状态为“可施工”、未确认项为 `0`。
- implement 完成：全部施工任务完成并有验证证据。
- test 完成：必需验证通过且 `003-测试文档.md` 的用例、证据和结论一致。
- close 完成：`status.md` 为 `done / 已关闭 / 100%`，知识沉淀与 AI 登记结果已记录。

不得用“文件存在”替代这些条件。

## 自动决策边界

AI 可以自动决定低风险、可逆、不改变需求口径的实现细节，并记录理由。遇到以下事项必须暂停等待用户：

- 产品或业务语义；
- 安全、权限、隐私和合规；
- 数据破坏、生产执行或不可逆迁移；
- 对外接口、长期兼容和外部承诺；
- 工作范围显著扩大；
- 跳过未执行测试并接受未验证风险；
- 用户明确要求参与的决定。

Solo 不处理 Debug 或 Script 工作流，也不跳过 implement 的强制施工压测。

## 推进与完成

1. 记录检测出的当前阶段、证据、缺口和目标阶段。
2. 确认 `workflow=standard`，按 `design.md`、`delivery.md` 依次推进；其他 workflow 立即拒绝并返回对应独立入口。
3. 每个阶段开始、完成和自动跳转时调用状态脚本；脚本同步 `status.md` 投影，有可信 sessionId 时再同步 AI 登记。
4. 遇到待用户决策、授权不足、重大设计缺陷或环境阻塞时暂停并报告证据。
5. 标准测试全部通过后用 `test` 命令写入证据并进入 `test / 待关闭 / 95%`，然后自动执行 `close-request`、文档收口、知识沉淀、AI 登记和 `close-complete`；成功后以 `done / 已关闭 / 100%` 结束，不再等待用户另行输入 Close。
6. 如果测试完全未执行或用户要求省略测试，Solo 不得自动代替用户接受风险。先运行 `close-request` 生成绑定当前工作树的一次性确认请求，按 `close.md` 提醒并暂停；只有用户二次确认后，才运行 `close-confirm` 并继续收口。
7. 从已完成 Test 的任务启动 Solo 时直接执行 Close；任务已经关闭时只做幂等校验和结果汇报，不重复生成记录。
